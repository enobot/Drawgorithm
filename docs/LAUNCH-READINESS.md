## What the site collects and stores

From the code (`src/state/store.ts`, `src/ui/App.tsx`, `src/auth/`) and the Supabase library source:

| What                                              | Where                                                                                              | Why                         |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------- | --------------------------- |
| The learner's code, inputs and settings           | The browser's `localStorage` (`drawgorithms:v1`)                                                   | Keeps work between visits   |
| Panel sizes                                       | `localStorage` (`drawgorithms-panels`, `drawgorithms-panels-medium`)                               | Keeps the layout            |
| Sign-in session (only when signed in)             | `localStorage`: `@supabase/auth-js` uses `globalThis.localStorage` in browsers (`GoTrueClient.js`) | Stays signed in             |
| Email address and password (only with an account) | Supabase Auth; passwords are handled by Supabase, never by this app's code                         | The account                 |
| IP address and user agent of sign-in events       | Supabase Auth audit logs ([Supabase docs](https://supabase.com/docs/guides/auth/audit-logs))       | Supabase's security logging |

- **No cookies.** Neither the app nor `@supabase/supabase-js`/`auth-js` writes `document.cookie` (checked in the installed source). Check the live site's responses for `Set-Cookie` after the first deploy.
- **No analytics, error reporting or tracking**, and no requests to any server other than this site and Supabase (the Content-Security-Policy allows only those two).
- **No third-party embeds or scripts**: fonts are bundled (`@fontsource`), the editor and Python run from this site.
- Learners' code runs in the browser and is never sent anywhere. Accounts do not save code or progress yet (`docs/ACCOUNTS.md`).

The goal is to collect only what is needed. **Sign-in is on at launch** so the number of accounts can be counted (decided 2026-10-28, later the same day, replacing an earlier “off at launch”; [decision 2](#open-decisions)). The live build therefore needs the Supabase settings (without them the app shows no sign-in, `src/auth/AuthUI.tsx`), and the email, password and sign-in-log rows above apply from launch. [PRIVACY-AND-TERMS-PLAN.md](PRIVACY-AND-TERMS-PLAN.md) plans the privacy policy and terms around them.

## Accessibility

**Method** (scripts kept outside the repository; rerunnable on request):

- [axe-core](https://github.com/dequelabs/axe-core) 4.14.0 (Deque, MPL-2.0) with the WCAG 2.0, 2.1 and 2.2 A and AA rule tags, on 19 screens: first visit, problem/code/visual tabs, both practice lists, the lesson list, an exercise with hints and the reference open, the answer walkthrough, a lesson, sign-up and log-in dialogs, and the Illustrated and Both picture styles for arrays, trees, linked lists, queues, tree building and binary search. Each at 1440×900 and 375×812.
- A contrast check by pixels for text axe cannot judge (gradients, drawings): two screenshots at 2× (with and without text) give each text's rendered glyph color against what is behind it, so translucent overlays and halos are measured as seen. Threshold 4.5:1, or 3:1 for large text (WCAG 1.4.3).
- A keyboard-only run: every Tab stop up to the code editor, leaving the editor, and opening and closing each dialog.

**After the fixes:** 0 axe violations and 0 texts below the contrast minimum on all 38 screen/size runs, and all keyboard checks pass.

**Reviewed, not changed**

- Symbol buttons (✕, +, −) are named for what they do (“Close”, “Zoom in”). W3C: “text should not be considered a visible label if it is used in a symbolic manner” ([Understanding 2.5.3](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html)).
- In the technical linked-list drawing, a node ending in “null” is named “node 4, next is null”; axe wants “4 null” together. “null” is the node's pointer value, not its label, and the W3C page limits 2.5.3 to text that labels a control.
- On phones the floating zoom controls can sit over the bottom edge of a drawing; the board scrolls it clear.

**Not covered:** screen readers (NVDA, VoiceOver, TalkBack) were not tried by hand; only Chromium was tested (Firefox and WebKit were installed later that day for the cross-browser check under [Verification run](#verification-run); the accessibility checks were not re-run in them); no real phones; contrast was checked at one step of each drawing, not every step; the editor's own widgets come from Monaco.

**Why it matters legally:** the Justice Department states that the ADA applies to the websites of businesses open to the public and points to WCAG as guidance, without a required standard ([ADA.gov, 2022-03-18](https://www.ada.gov/resources/web-guidance/)). In California a violation of the ADA is also a violation of the Unruh Civil Rights Act ([Civil Code § 51(f)](https://leginfo.legislature.ca.gov/faces/codes_displaySection.xhtml?lawCode=CIV&sectionNum=51)), with damages of “no case less than four thousand dollars ($4,000)” per offense ([§ 52(a)](https://leginfo.legislature.ca.gov/faces/codes_displaySection.xhtml?lawCode=CIV&sectionNum=52)).

## Security

- **Dependency advisory fixed.** `monaco-editor` 0.57.0 pins `dompurify` 3.4.15, which has critical and high advisories ([GHSA-cg2g-xh64-v4q7](https://github.com/advisories/GHSA-cg2g-xh64-v4q7), [GHSA-mrv2-3pqr-j5jr](https://github.com/advisories/GHSA-mrv2-3pqr-j5jr) and three more), all patched in 3.4.17. `package.json` now [overrides](https://docs.npmjs.com/cli/v11/configuring-npm/package-json#overrides) that one nested version; `npm audit` reports 0 vulnerabilities. The editor's hover tooltips (which use DOMPurify) were checked in the app.
- **No secrets** in any tracked file or in the history of any branch (searched for Stripe, Supabase secret, service-role JWT, AWS and private-key patterns). `.env.local` is ignored, and the app refuses a Supabase secret key (`src/auth/config.ts`).
- **Headers:** Content-Security-Policy (scripts only from this site; network only to this site and Supabase; no framing), `nosniff`, a strict referrer policy and a permissions policy. `src/headers.test.ts` fails if `public/_headers` and `vercel.json` ever differ.
- **CI** runs types, lint, every test, formatting, the build, the licence-notice check and `npm audit --audit-level=high` on every push and pull request.
- **Still open, in the Supabase dashboard** (your account): leaked-password protection was found disabled ([Supabase docs](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)); production Site URL and Redirect URLs; custom SMTP; CAPTCHA for sign-up (`docs/DEPLOYMENT.md`).
- No system can be made unhackable. There was no penetration test. The design keeps the attack surface small: no server code of our own, no database tables, learners' code in a sandboxed worker.

## Payments (Stripe): design, not built

No payment code exists. When there is something to sell:

1. Stripe Checkout (Stripe's hosted page), so card details never touch this site.
2. Two Vercel Functions: one creates a Checkout session for the signed-in user; one receives Stripe's webhook, verifies its signature, and records the plan.
3. A Supabase `profiles` table with row-level security: users can read only their own row; only the webhook (with the secret key, server-side) can change a plan (`docs/ACCOUNTS.md`).
4. Before launch: a refund policy, the Automatic Renewal Law items above, updated Terms, Vercel Pro, and the CSP updated for Stripe's domains, each checked against Stripe's and Vercel's documentation at the time.
